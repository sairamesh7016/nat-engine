STATEFUL IPv4 NAT ENGINE — PROJECT REQUIREMENTS

---

1. TITLE

Stateful IPv4 NAT Engine
A userspace IPv4 Network Address Translator with full connection tracking, TCP/UDP/ICMP state machines, fragmentation handling, and a Python test harness with correctness checks and telemetry.

---

2. PROBLEM IT SOLVES

NAT is the canonical "systems + networking" problem. It exercises every C systems skill: hash tables, state machines, timers, memory management, pointer arithmetic, and checksum math. It's harder than it looks — port collisions, TCP sequence handling, ICMP ID mapping, fragmentation across NAT boundaries, and TIME_WAIT aging are the parts that separate a toy from a real implementation.

This project proves you can build the transport-layer state machine that home routers and carrier gateways run. It's the most self-contained of the three projects (no kernel/root complexity, no special hardware), so it's the fastest path to a working demo and builds your C systems credibility before tackling SRv6 and eBPF/XDP.

---

3. USE CASE

- Learning: understand connection tracking, SNAT/DNAT, TCP state machines, port mapping, aging, and fragmentation.
- Portfolio: a GitHub repo demonstrating C systems programming + Python test harness + networking.
- Interview talking point: "I built a stateful NAT from scratch — here's the connection table, here's how I handle port collisions, here's how UDP pseudo-connections age, here's how I reassemble fragments across the NAT boundary."
- Demo: two network namespaces connected by the NAT, ping/tcp through it, verify bidirectional connectivity and port preservation.

---

4. HIGH-LEVEL DESCRIPTION

A userspace NAT that tracks TCP/UDP/ICMP connections, maps private IPs/ports to public ones, and handles the full state machine.

C DATA PLANE:
- Connection tracking table (hash by original 4-tuple, lookup on reply)
- SNAT (source NAT) on outbound, DNAT (destination NAT) on inbound
- TCP state machine (SYN → ESTABLISHED → FIN → TIME_WAIT)
- UDP pseudo-connection aging
- ICMP ID tracking
- IP fragmentation reassembly across NAT boundaries
- NAT table aging (TIME_WAIT expiry, idle timeout, port exhaustion detection)
- CLI: show nat, show conn, show stats, flush

PYTHON TEST / CONTROL PLANE:
- Namespace topology setup (veth pairs + namespaces) or TUN/TAP
- Traffic generator (send packets through the NAT)
- Correctness checks (same session returns to same mapped port, bidirectional connectivity preserved, no port collisions)
- Stats: active connections, bytes translated, translation errors
- Telemetry: connection count over time, per-rule byte/packet counters, latency percentiles

8. INTERACTIONS

1. Python → C (config): nat_client.py pushes NAT mappings (SNAT/DNAT rules, timeouts) to the C engine.
2. C → C (forwarding): packet arrives → conn tracking lookup → SNAT/DNAT rewrite → forward out interface.
3. C → Python (telemetry): after each packet, conn counts, bytes, latency counters are collected and reported by the Python harness.
4. Python → Python (test): nat_test.py sets up namespaces, generates traffic, and asserts correctness (port preservation, bidirectional connectivity, no collisions).

10. KEY DATA STRUCTURES

struct nat_conn {
    uint32_t src_ip, dst_ip;       // original
    uint16_t src_port, dst_port;
    uint32_t nat_ip;               // mapped public IP
    uint16_t nat_port;             // mapped port
    uint8_t  proto;                // 6=TCP, 17=UDP, 1=ICMP
    uint8_t  state;                // TCP state (0=NEW..4=TIME_WAIT)
    uint64_t bytes_out, bytes_in;
    uint64_t last_seen;
    uint64_t created;
    struct nat_conn *hnext;        // hash chain
};

struct nat_table {
    struct nat_conn **buckets;     // hash table
    size_t bucket_count;
    size_t conn_count;
    uint64_t total_bytes;
};

11. EXAMPLE / DEMO

# Build
$ make
$ python -m venv .venv && source .venv/bin/activate

# Start the NAT engine between two namespaces
$ sudo python nat_test.py --topo configs/nat-topo.yaml
Setting up namespaces...
NAT engine started on veth0 <-> veth1

# Inside namespace A: ping through the NAT
$ ip netns exec ns-a ping 8.8.8.8
PING 8.8.8.8 (8.8.8.8) 56(84) bytes of data.
64 bytes from 8.8.8.8: icmp_seq=1 ttl=63 time=12.4 ms

# Inside namespace B: tcpdump shows the SNAT rewrite
$ ip netns exec ns-b tcpdump -i veth1 -n
12:34:56.789 IP 203.0.113.7:45001 > 8.8.8.8:80  (SNAT applied)

# Show connections
$ natctl show conn
  192.168.1.5:49152 → 203.0.113.7:45001  TCP  ESTABLISHED  1.2MB
  192.168.1.6:53211 → 203.0.113.7:45002  UDP  ACTIVE       45KB

# Show stats
$ natctl show stats
  connections=147 | bytes_out=4.2GB | drops=0 | avg_latency=0.8ms

14. NOTES FOR IMPLEMENTATION

- Pure C + Python only. No Go, Java, Rust, or other languages.
- No special hardware. Needs root/sudo for namespaces/veth (WSL2 Ubuntu 22.04+ works; bare Windows does NOT — use WSL2).
- Keep the C data plane self-contained and testable in isolation — the conn tracking + rewrite path should work with a simple loopback test before namespaces are added.
- Telemetry format: JSON, consistent with the other two projects (srv6-engine, xdp-filter) so the portfolio tells one coherent story.
- Naming conventions: snake_case for C, snake_case for Python, kebab-case for file/directory names.
- README structure (same in all 3 projects): overview, architecture diagram, features, build instructions, demo, telemetry output.
- Port allocation strategy: track used ports per NAT IP in a bitmap or linked list; start from 1024; avoid well-known ports.
- TCP sequence randomization is optional for v1 — note it as a known limitation in the README rather than trying to implement it in the first pass.
